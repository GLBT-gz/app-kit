### 2026-08-24：页面边距反复出错——`.main-content` 默认 padding 与 `:has()` 反覆盖的模板级缺陷（013 案例）

**症状**（013-面单回传，两处同时出现）：
1. 测试页整体多出一圈 24px 边距，内容被挤压；
2. 设置面板「账密登记」tab 内容完全贴边（无任何边距）。

**根因**（模板层两套边距语义打架，新项目复制老项目代码必然踩坑）：
- `components.css` 的 `.main-content` 自带 `padding: 24px`（旧体系遗留），而 `base.css` 新体系声明 `.page-content` 无 padding、普通页用 `.page-padded`。全屏页若误挂 `.main-content`，必须在项目 CSS 用 `:has()` 反覆盖——但 `:has()` 选择器依赖共享组件内部 DOM 结构。013 的测试页选择器写的是 `.main-content:has(> .test-panel)`（直接子代），而 TestPanel 内部多包了一层 div，匹配失败，padding 没被去掉。007 能正常纯属其 TestPanel 恰好把 `.test-panel` 作为根元素直接返回。
- `.settings-content` 容器无 padding，约定每个 tab 内容自带边距。`DataManagerPanel`/`ShortcutsPanel`/`BrowserConfigPanel` 都自带，唯独 `CredentialsForm` 裸奔——007 里它嵌在 `AutomationSettings` 的内联 `padding: 0 28px` 包装层里才正常，013 直接当 tab 内容用就贴边。

**修复**：
1. 013：全屏页（业务页/测试页）根节点去掉 `.main-content` 类（按 base.css 约定全屏页不加边距类）；CredentialsForm 裸用时传 `padded` prop。
2. 共享层：`CredentialsForm` 新增 `padded?: boolean` prop（默认 false，老项目零影响），裸用时自带 `24px 28px`。
3. 规范：`代码规范.md` 新增「页面边距规范」；`.main-content` 定义处加注释禁止全屏页使用。

**关键经验**：

```
普通页   → .page-padded（新）或 .main-content（旧，仅普通页可用）
全屏页   → 不加任何边距类，页面组件自带布局（禁止 .main-content + :has 反覆盖）
设置 tab → 内容组件必须自带 padding；CredentialsForm 裸用传 padded，嵌 AutomationSettings 不传
复制老项目代码时，其 CSS 里的 :has() 反覆盖是历史包袱信号，不要照抄，按上表重新归类页面类型
```

**验收**：013 各标签页、设置面板各子页边距与 007/012 视觉一致。

### 2026-08-19：浏览器配置三条路径规则的实证验证（默认路径不可自动化 / 同路径多用户 / 不同路径并行）

**背景**：「当前浏览器配置」界面对 profile 分三档：默认路径=完全受限（不可用于自动化控制）、同 user-data-dir 多用户=部分受限、单用户目录=完全可用（见 `CurrentBrowserCards.tsx` 的 `isDefaultUserDir` / `isMultiUserDir`）。规则源自 `a41bbe5`（2026-07-31 中性化迁移，从原 EDecker 项目带入），仓库内此前**无独立实验记录**。本次用本机 Edge 做受控实测，结论如下。

**结论**：
- ②「同路径多用户不能同时控制」= **硬约束（真实）**。Chromium 对每个 user-data-dir 施加单实例锁（ProcessSingleton / SingletonLock），同目录第二个实例的命令行被转发给已有实例、新进程立即退出，`--remote-debugging-port` 被静默忽略。
- ③「不同路径单用户可同时操作」= **真实**。各目录锁独立，互不冲突，可并行运行多个实例。
- ①「默认路径不可自动化」= **条件性真实（表述偏绝对）**。真正原因是：默认目录几乎总被用户日常浏览器占用 → 单实例转发导致调试端口不开；Chrome 136+（2025 起）官方安全策略明确要求 `--remote-debugging-port` 必须配合**非默认** user-data-dir，否则拒绝启动（报错 `DevTools remote debugging requires a non-default data directory`），Chrome 147+ 默认阻止并弹「允许」确认（Edge 未见同限制）；以及安全/防破坏考量（自动化默认目录=劫持用户真实 cookie/登录态）。严格表述应为「默认目录**被占用时**不可自动化」，目录空闲时（浏览器完全关闭）Edge 实际可以开调试端口。

**实测记录**（本机 Edge，受控实验，事后已清理全部进程/目录/端口）：

| # | 场景 | 结果 |
|---|---|---|
| TEST1 | 独立临时目录 + 调试端口 9333 | 端口 OPEN |
| TEST2 | 同目录已有实例，再启动同目录 + 9334 | 端口 CLOSED，新进程自动退出 |
| TEST3 | 目录 A 运行中，启动目录 B + 9335 | 端口 OPEN（两实例并行） |
| 对照 | 后台无窗口进程占住目录 C，再启动同目录 + 9338 | 端口 CLOSED，新进程退出 |
| TEST6 | 默认目录被后台主进程（`msedge.exe --no-startup-window`）占用，启动默认目录 + 9339 | 端口 CLOSED，新进程退出 |

无效实验（供后人避坑）：headless 模式会强制用临时目录 `%TEMP%\HeadlessEdge<pid>`，忽略 `--user-data-dir`（TEST4 因此无效）；含空格的路径传给浏览器必须加引号，否则 `--user-data-dir=C:\...\Edge\User Data` 会被截断成 `...\Edge\User` 导致测到的是新目录而非默认目录（TEST5 因此无效，且会在 Edge 目录下留下截断路径目录，需清理）。

**关键经验**：
- 验证「某 user-data-dir 是否被占用」不能只看进程命令行里有没有该字符串——`--no-startup-window` 的后台主进程命令行里**根本没有路径**（走默认目录），要结合 `SingletonLock` 文件 / 有无 `--type=` 的主进程综合判断。
- 同目录并发被禁是浏览器设计（单实例锁），不是本工具的限制；本工具 `start_or_connect` / `debugLaunchWithLockCheck` 的杀旧进程逻辑正是在释放这把锁。
- 规则①在代码里的实现是「前端策略」而非后端硬限制：默认目录卡已支持 启动/命令/快捷方式（不带调试端口），只是不可「调试打开」、不可被选为自动化控制对象。

### 2026-08-18：「当前浏览器配置」tab 滚轮卡顿——同步 Tauri 命令阻塞主线程

**症状**：设置面板滚轮快速切换，切进/停留在「当前浏览器配置」tab 时卡顿。修复前每次卡 1~4s，原生枚举后仍「稍微卡住」（每次滚到该 tab 顿一下）。

**根因**（两层，逐层修复）：
- `detectBrowserRunningProcesses` 是 Tauri v2 **同步命令**（非 async）→ 官方文档明确「非 async 命令在主线程执行」。`on_message` → `run_invoke_handler` 在 UI 线程同步执行命令体，主线程事件循环（含滚轮消息）被堵死。
- 后端实现每次 spawn 两个 PowerShell 子进程（msedge/chrome 各一次 `Get-CimInstance Win32_Process` 枚举全系统进程）+ wmic 回退，`Command::output()` 同步等待 → 单次 1~4s。
- 原生枚举后仍卡：命令**仍是同步跑主线程**——浏览器进程多时（每标签页 5~10 个进程、命令行数十 KB）原生扫描可达数十 ms，加上 `check_cdp_reachable` 单端口 1500ms 超时，恰好撞上滚轮瞬间。
- 触发频率：tab 可见即检测 + 每 5s 轮询（CurrentBrowserCards `POLL_INTERVAL_MS=5000`）。

**修复**（A+B 双管齐下）：
1. `tauri_bridge.rs`：`detect_browser_running_processes` 改 **async fn + spawn_blocking** → 检测彻底移出主线程（进程枚举 / TCP 检测多慢都不卡 UI）。
2. `browser_process.rs` 三处（`scan_running_browser_instances` / `scan_running_browser_processes` / `is_running_instance_headless`）改 Windows 原生枚举：CreateToolhelp32Snapshot 快照 → 按 exe 名过滤 → OpenProcess + NtQueryInformationProcess(`ProcessCommandLineInformation=60`) 读命令行（Buffer 同时处理「随头拷入输出缓冲区」与「指向目标进程内存需 ReadProcessMemory」两种形态）→ 走原解析路径，行为不变。
3. `check_cdp_reachable` 超时 1500ms → 300ms（本机回环开/拒即时返回，超时仅是兜底）。
4. 删除 `parse_process_json` / `parse_wmic_list` 及 `decode_windows_stdout` 依赖。

实测：单次检测 0.02s；cargo test 端到端验证原生枚举能读到自己进程命令行。

**关键经验**：
- Tauri v2 同步命令跑主线程；凡涉及 spawn 子进程 / 进程枚举 / 网络超时的命令，**必须 async fn + spawn_blocking**，光换快实现不够（几十 ms 也会在滚轮瞬间被感知）。
- 轮询型检测（5s 一次）绝不能走子进程；进程命令行枚举用 Toolhelp32Snapshot + NtQueryInformationProcess。
- 本机回环 TCP 检测的超时不要设 1.5s，300ms 足够，防异常端口拖慢同步路径。

### 2026-08-14：设置面板滚轮切换卡顿——懒挂载 + 重复检测（多层叠加）

**症状**：刷新（Ctrl+R）后第一时间在设置面板最左侧 tab 列表滚轮快速切换，滚轮不跟手，会在某个 tab 卡上几秒后恢复（0.5~1.5s）。

**根因**（多层叠加，逐层修复）：

1. 配置页间切换重复触发后端检测——`refreshBrowserData()` 只有 in-flight 去重，BrowserConfigSection / CurrentBrowserCards 各自挂载都触发第二轮完整扫描（注册表 + Preferences.json + 头像缩略）+ 400ms 最短 loading。
2. 设置 tab 切换把内容渲染包 `startTransition` 降级，而检测完成的全量渲染是同步 setState → 主线程忙时高亮已变、内容滞后。
3. BrowserConfigInner 挂载 800ms 后自动 `detectCustomProfiles`，与 store 检测重复扫描同一批目录 + 返回后全量卡片渲染。
4. **根本**：AppLayout `mountedTabs` 懒挂载——滚轮首次经过某 tab 时同步渲染重 content（数据管理大 JSON / 浏览器卡片列表），主线程阻塞卡数秒。

**修复**：

- **页面层叠**（核心）：设置面板打开后 `requestIdleCallback` 空闲时逐帧预挂载全部 tab（display:none 不可见），滚轮切换纯 display 切换零渲染；空闲执行不抢用户交互（timeout 1500ms 兜底）。
- `refreshBrowserData(force=false)` 加 lastSyncedAt 会话内去重，「重新检测」按钮传 `force=true`。
- 设置 tab 切换同步 setState（不用 startTransition）；检测完成的全量渲染包 `startTransition` 降为低优先级。
- profiles 单一数据源：删 BrowserConfigInner 自动检测，卡片同步 `browser.profiles`（store 检测结果）。

**关键经验**：

```
设置面板 tab 切换流畅度 → 禁止懒挂载「首次访问才渲染」；用页面层叠（空闲预挂载全部层）
后台检测/加载完成的大渲染 → 包 startTransition 降级；用户交互（切换）同步高优先级
浏览器检测 → 只在进配置页触发一次（browserStore 去重），配置页组件挂载不得各自重复检测
```

**验收**：刷新后立即滚轮快速切换设置 tab，全程跟手无卡顿。

### 2026-08-13：层叠页面只加 opacity:0 隐藏 → Ctrl+F 检索出隐藏标签页内容

**症状**：007-库存周转 的表格页面用 Ctrl+F 检索，结果不准确——会跳到其他标签页的匹配内容，看起来「结果错乱」。

**根因**：页面切换用「全部页面常驻 DOM + 绝对定位层叠 + `opacity: 0` + `pointerEvents: none`」隐藏非活跃页（保留状态、切换丝滑）。但浏览器 Ctrl+F（find-in-page）搜索的是**文档全部文本**，`opacity: 0` 的元素仍在 DOM 中、可见性未被排除，所以检索会命中所有隐藏页的文本。

**修复**：非活跃页面容器补加 `visibility: hidden`（与 opacity/pointerEvents 同条件切换）。`visibility: hidden` 的元素不参与 find-in-page 搜索，同时保留层叠、状态、合成层优化。

```tsx
// ✅ 正确：opacity + visibility + pointerEvents 三件套（每页同条件）
style={{ ...PAGE_STYLE, opacity: active ? 1 : 0, visibility: active ? "visible" : "hidden", pointerEvents: active ? "auto" : "none" }}

// ❌ 错误：只用 opacity: 0 —— Ctrl+F 命中隐藏页文本
// ❌ 错误：用 display: none —— 能排除搜索但切换触发完整 layout，牺牲性能（07-29 已论证）
```

**关键经验**：

```
opacity: 0           → 视觉隐藏，但 Ctrl+F 仍会命中（DOM 中可见性未排除）
visibility: hidden   → 视觉隐藏 + 排除 find-in-page 搜索（同时不触发 layout）
display: none        → 排除搜索但触发完整 layout（层叠方案禁用）
→ 层叠方案隐藏非活跃页必须：opacity + visibility:hidden + pointerEvents:none
```

**验收**：切到任意标签页后 Ctrl+F，结果只来自当前可见页。

> 规范条目见 `glbt-apps/docs/自动化UI规范.md`「页面切换与隐藏」。

### 2026-08（补录）：通用工程坑——TS 6.0 / pnpm 虚拟目录 / Rust 编译依赖

**1. TS 6.0 弃用 `baseUrl`**

`tsconfig` 里 `baseUrl` 被弃用会报 deprecation，需加 `"ignoreDeprecations": "6.0"` 抑制。

**2. pnpm 的 `.pnpm` 虚拟目录会破坏 Node 原生 TS 加载**

`file:` 依赖会被 pnpm 放入 `node_modules/.pnpm` 虚拟目录。Node 的原生 TS 加载器（如 `--experimental-strip-types`）拒绝加载 `node_modules` 下的 `.ts`，导致共享源码无法直接 import。

```typescript
// ❌ 跨仓库共享不要用 file: 依赖直引（会被塞进 .pnpm 虚拟目录）
"@appkit/ui": "file:../../../app-kit/shared/ui"

// ✅ 用 vite.config.ts 源码直引，绕过 pnpm 虚拟目录
import { createViteConfig } from "../../../app-kit/shared/ui/src/vite-config.ts";
```

**3. `cargo check` 要求 `../dist` 存在**

Tauri 的 `build.rs` 里 `generate_context!` 宏会检查前端 `dist` 目录是否存在，不存在则编译失败。改 Rust 代码前需先 `pnpm build` 生成 dist。

**4. `pnpm install` 报 frozen-lockfile 错误**

新增依赖后 lockfile 未更新会报 `frozen-lockfile` 错误，用 `pnpm install --no-frozen-lockfile`。

**5. 旧工具链不支持 `const HashSet::new()`**

旧版 Rust 的 `HashSet`/`HashMap` 不支持 const 构造。`static` 里用 `Mutex<Option<HashSet<T>>>` + 惰性初始化：

```rust
static CACHE: Mutex<Option<HashSet<String>>> = Mutex::new(None);

fn cache_mut() -> MutexGuard<'static, Option<HashSet<String>>> {
    CACHE.lock().unwrap()
}

// 使用：惰性初始化
let set = cache_mut().get_or_insert_with(HashSet::new);
```

### 2026-08-03：git status 显示 modified 但 git diff 为空——行尾符（LF/CRLF）差异

**症状**：用编辑工具修改 `Cargo.toml`（如升版本号）后，`git status` 显示文件为 modified，但 `git diff` / `git diff --stat` 输出为空，仅提示 `LF will be replaced by CRLF`。

**根因**：编辑器写入的是 LF 行尾，而仓库内文件是 CRLF（Windows + `core.autocrlf` 环境）。git 比较工作区字节与 index 认为不同，但按行尾规则规范化后内容一致，所以 diff 为空。

**处理**：
```powershell
git add <文件>     # git 按 autocrlf 规范化，index 与 HEAD 一致，状态即清除
git commit ...     # 若暂存后提示 "nothing to commit" 属正常，直接忽略
```
**不要**提交一个空的"行尾规范化" commit。

**教训**：
- `git status` 显示 M 但 `git diff` 为空时，先怀疑行尾符，不要当作真实改动排查。
- 批量升版本号（多个 `Cargo.toml` 一起改）后最容易出现，逐个 `git add` 即可清除状态。

### 2026-07-29：前端渲染性能——多页面 + 大数据表格导致标签页切换卡顿

**症状**：007-库存周转项目中，页顶标签栏（TabBar）通过滚轮切换标签页时出现明显卡顿，CPU 100%。页面内部的子 tab 切换（日志 ↔ 表格）流畅。清空所有数据后标签栏切换恢复正常。

**问题复现条件**：
- 有 2+ 个数据表格页面加载了数据（如海多客 420 条 + 元仓 1k+ 条）
- 多维表格（KdocsPage）加载了全部平台汇总数据（~1500 条）

**临时排查**（通过清空子页面内容逐步定位）：

测试 | 排查方法 | 结论
---|---|---
清空多维表格页面 | 将 KdocsPage 返回内容改为纯文字 | **卡顿消失** → 根因是多维表格
清空海多客数据 | 不加载数据 | 依然流畅
加载海多客 + 多维表格数据 | 恢复 KdocsPage 并加载 | 卡顿复现

**根因**：

1. **KdocsPage 普通 `<table>` 渲染 1500+ 行未虚拟化** — 所有平台汇总的数据行通过 `.map()` 直接渲染为 `<tr>`，7 个页面同时存活（opacity 方案下），1500+ DOM 节点持续占用浏览器渲染管线。
2. **`display: none/flex` 切换需完整布局** — 隐藏页面的 VirtualTable（28000px spacer + 50 tr）在切换时需要浏览器做完整 layout 计算，比 compositing-only 切换慢。

**修复方案**：

| 改动 | 说明 |
|------|------|
| KdocsPage: 普通 `<table>` 替换为 VirtualTable | 只渲染可见行（~50 行），其余用 spacer 占位，1500+ → 50 DOM 节点 |
| 页面容器 `opacity: 0/1` + `willChange: "opacity"` + **`visibility: hidden`** | 通知浏览器保留合成层，切换仅 GPU compositing，无 layout；**visibility:hidden 同时排除 Ctrl+F 命中隐藏页（2026-08-13 补充，见本文件顶部条目）** |
| 移除 VirtualTable `will-change: transform` | 避免嵌套合成层（父 opacity 层 + 子 transform 层） |
| 页面组件 + VirtualTable + PageContent 包裹 `React.memo` | 阻止不必要的 React reconciliation |
| Columns/rowClassName 提取为模块常量 | 保证引用稳定，React.memo 生效 |
| ResizeObserver `offsetParent` 检查 | 隐藏时不触发 `setContainerHeight` |
| Scroll handler 同步捕获 `scrollTop` | 修复 `e.currentTarget` 在 rAF 回调中为 null 的 bug |
| `useData` 实现 Analysis | 确认 `useData` 是独立 per-key 的 localStorage 订阅，不会跨页级联 |
| AppContent 隔离 | 将 `activeTab` 从 App 提取到独立子组件，切换标签页时不触发顶层 hooks（useBrowserBaseData 等）重跑 |

**关键经验**：

```
所有页面同时用 opacity:0 隐藏时 → DOM 节点总量决定性能瓶颈
→ 非虚拟化表格（Kdocs 1500+ tr）是灾难
```

### 2026-07-25：日志级别名称不匹配——后端"ok" vs 前端"success"

**症状**：自动化页面和测试页面的日志中，成功步骤显示为灰色（info 级别），看不到绿色成功日志。用户反馈"很少有绿色日志"。

1. 后端 Rust 代码使用 `emit(&progress, "ok", msg)` 发送日志，level 值为 `"ok"`。

```typescript

```

**修复**（两处都需要改）：

1. **后端 emit 函数** — 若创建新的日志发射函数，应使用标准级别名：

   ```rust
   emit(&progress, "info", "正在处理...");

   emit(&progress, "error", "失败...");
   ```

2. **前端事件监听** — 如果后端已固定用"ok"，则必须做映射：
   ```typescript

   listen(eventName, (event) => {
     const level = event.payload.level === "ok" ? "success" : event.payload.level;

   });
   ```

**跨项目检查结果**（确认仅 007 受影响）：

| 项目 | 日志发射方式 | 是否存在"ok"问题 |
|------|-------------|:--------------:|

### 2026-07-24：CDP 模拟输入——React 异步搜索要求 `isTrusted=true`

```rust

// ❌ 不应使用 JS input.value（产生 isTrusted=false 事件）

input.dispatchEvent(new Event('input', { bubbles: true }));
```

**教训**：
- React/Ant Design 依赖 `isTrusted` 标志来区分用户操作和程序模拟
- CDP 级别的 `Input.insertText` / `Input.dispatchKeyEvent` 能产生受信事件
- 遇到"设置了值但组件没反应"的问题，优先排查事件是否为 `isTrusted=true`

### 2026-07-11：前端数据持久化——三层缓存架构

**症状**：用户在浏览器配置界面修改路径/筛选后，快速刷新（Ctrl+R）或切换 Tab，修改丢失。

**根因**：数据需要经过两层 React 渲染周期才能到达 `useEffect` 的 `localStorage.setItem`，在此期间用户刷新会导致数据丢失。

**修复方案——三层优先链**：

```
层1：React State（内存，最快）        ← 用户操作的直接目标
层2：localStorage（磁盘，快）          ← 同步写入，刷新时恢复
层3：后端配置文件（Tauri IPC，慢）     ← 异步写入，永不覆盖层2
```

核心规则：
1. **写路径**：层1 → 立即同步写层2 → 异步写层3（fire-and-forget）
2. **读路径**：从层2恢复 → 层3只填补层2的空白，**永不覆盖**
3. **层3永远不能覆盖层2已有的值**

具体手段：
- 使用 `useLayoutEffect` 代替 `useEffect` 写缓存，保证在浏览器绘制前同步写入 localStorage。
- 合并后端数据时，`prev[bt] !== undefined` 则跳过，缓存优先。
- 对于深层嵌套的子组件，直接在组件内独立持久化到 localStorage，不依赖父组件链路。

**教训**：
- `useEffect` 的回调在浏览器绘制后才执行，不能保证刷新前落盘。
- 组件链路越长，数据到达目标组件的时间越不确定，直接在目标组件做 localStorage 持久化更可靠。

## 常见问题

### 构建失败：`STATUS_ILLEGAL_INSTRUCTION`

**原因**：链接器阶段 CPU 指令集不兼容。
**解决**：先运行 `cargo build --release` 单独编译 Rust，编译通过后再运行 `npx tauri build`。

### 安装包下载后只有几 KB

**原因**：版本服务器 404（中文文件名 URL 编码未解码），返回了 HTML 错误页作为下载内容。
**解决**：确认 `server.py` 已包含 `from urllib.parse import unquote`，并在文件查找前调用 `unquote()`。

### Windows 上启动 Python 服务器

```powershell
# 使用 venv 中的 python
<venv路径>\Scripts\python.exe server.py

# 或者使用系统 python
python server.py
```

注意：Windows Store 安装的 Python stub 可能无法通过 `Start-Process` 正常启动，建议直接用 venv 路径。
